1. PROJECT OVERVIEW
================================================================================
The existing "Ticket Booking System" (11 Spring Boot microservices + React
frontend, PostgreSQL, Redis, Zipkin, Docker) is converted into an
ENTERPRISE-GRADE RESTAURANT TABLE RESERVATION PLATFORM.

Instead of movies / theatres / screens / seats / tickets, the platform now
manages:
    RESTAURANTS -> DINING AREAS -> TABLES -> TIME SLOTS -> RESERVATIONS
plus three signature features:
    (a) SMART TABLE MATCHING   - best table for your party size & preferences
    (b) LIVE TABLE HYGIENE     - is the table clean? live cleaning status board
    (c) PRE-ORDERING           - order food while you reserve, ready when seated

Multiple restaurants are supported (same multi-entity structure as the
original multi-movie system).

TECH STACK (unchanged):
  Backend  : Java 21, Spring Boot 3.2.5, Spring Cloud Gateway, Eureka,
             Spring Cloud Config, Spring Data JPA, PostgreSQL 16, Redis 7,
             Resilience4j, Micrometer + Zipkin, Swagger UI
  Frontend : React 18, TypeScript 5.5, Vite, TailwindCSS, React Router v6,
             Axios, React Hot Toast, Lucide React
  Deploy   : Docker Compose (15-16 containers), Maven multi-module

4. SMART TABLE MATCH ALGORITHM ("Best Table Matches")
================================================================================
 Given a party size, date, time slot, restaurant and preferences, the system
 scores every candidate table that is FREE (no active reservation on that
 slot) and hygienically READY (see section 5).

 SCORING FACTORS (higher = better match):
   1. Capacity fit          : exact capacity match scores max; table capacity
                              >= party size and <= party size + 2 preferred
   2. Wasted seats          : penalty for empty seats (capacity - party size)
   3. Zone preference       : WINDOW / PRIVATE / OUTDOOR / BAR / FAMILY /
                              LOUNGE - matching preference boosts score
   4. Accessibility         : wheelchair-accessible tables boosted for
                              accessibility requests
   5. Quiet corner          : tables flagged "quiet" boosted when requested
   6. Cleaning readiness    : CLEAN (READY) tables always outrank tables in
                              CLEANING (cleaning ETA used as tie-breaker)
   7. Location convenience  : tables near entrance / restroom per preference
   8. Multi-table grouping  : for very large parties, adjacent tables are
                              combined into one match (ReservedTable group)

 OUTPUT: ranked list of "best matches" with a MATCH SCORE (%) and human
 readable reasons, e.g.:
   "Table 7 - Window zone, seats 4 - 100% match (perfect size)"
   "Table 12 - Outdoor, seats 6 - 82% match (2 seats wasted, being cleaned,
    ready in ~10 min)"

 ENDPOINT:  GET /api/tables/match?restaurantId&date&time&partySize
            &zone&accessible&quiet

5. LIVE TABLE HYGIENE / CLEANING STATUS SYSTEM
================================================================================
 Every table carries a live cleaning state machine:

    READY  ->  RESERVED  ->  OCCUPIED  ->  DIRTY  ->  CLEANING  ->  READY
    (clean)  (on hold)    (seated)    (needs  (staff   )       (available)
                                        cleaning) sanitizing)

 RULES & AUTOMATION
   * A reservation HOLD locks a table as RESERVED.
   * When guests are seated (staff marks OCCUPIED), a PRE-ORDER placed by the
     guest is automatically released to the kitchen.
   * When guests leave, staff marks the table DIRTY (auto-suggested).
   * Staff starts cleaning -> status CLEANING with an estimated finish time
     (cleaningDurationMinutes + startedAt).
   * Cleaning completes -> status READY, and a cleaning LOG entry is stored
     (timestamp, staff, action).
   * WAITLIST users waiting for a table of that size are automatically
     notified the moment a matching table becomes READY.

 CUSTOMER VISIBILITY (on the table map):
   GREEN  = READY (book it now)
   BLUE   = RESERVED (held for another party)
   RED    = OCCUPIED (in use)
   BROWN  = DIRTY (cleaning needed)
   AMBER  = CLEANING - "being cleaned, ready in ~10 min"
   PURPLE = your selected table

 STAFF ENDPOINTS:
   PUT /api/tables/{id}/cleaning   {status: OCCUPIED|DIRTY|CLEANING|READY}
   GET  /api/tables/{id}/cleaning-log

6. PRE-ORDERING SYSTEM (attached to reservation)
================================================================================
 MENU (owned by restaurant-service)
   MenuItem: name, category (STARTERS/MAINS/DESSERTS/DRINKS), price,
   dietary tags (VEG / NON_VEG / VEGAN / GLUTEN_FREE / JAIN), spice level,
   prepTimeMinutes, availability, restaurantId.

 PRE-ORDER FLOW
   1. While reserving, the customer builds a pre-order from the menu.
   2. Pre-order total is shown inside the reservation summary and added to
      the required deposit (or shown separately).
   3. On seat-in (staff marks OCCUPIED), the pre-order status flips
      DRAFT -> PLACED and the kitchen receives it.
   4. Kitchen/waiter updates: PLACED -> IN_PREP -> SERVED.
   5. Estimated serve time is displayed to the guest.

 PRE-ORDER LIFECYCLE: DRAFT -> PLACED -> IN_PREP -> SERVED (or CANCELLED)


================================================================================
7. RESERVATION LIFECYCLE & TABLE LOCKING
================================================================================
  1. Customer searches restaurants -> opens detail -> picks date + service time.
  2. System shows the interactive TABLE MAP with live cleaning status +
     SMART MATCH suggestions.
  3. Customer selects 1+ tables (multi-table for large parties) + optional
     pre-order items.
  4. createReservation -> tables are LOCKED (RESERVED status) with a 15-minute
     payment hold; reservation status = HOLD.
  5. confirmReservation -> customer pays DEPOSIT via payment-service;
     status = CONFIRMED; a confirmation code + notification is issued.
  6. Seated (staff) -> OCCUPIED + pre-order released to kitchen.
  7. Completed -> status COMPLETED; tables auto-marked DIRTY -> cleaning flow.
  8. Cancellation -> status CANCELLED; deposit refunded; tables released to
     READY; waitlist checked for instant reassignment.

 STATUSES: HOLD -> CONFIRMED -> SEATED -> COMPLETED / CANCELLED


================================================================================
8. WAITLIST SYSTEM
================================================================================
 If no table matches (or all matching tables are OCCUPIED/DIRTY), the
 customer can join a TABLE WAITLIST with party size + preferred time window.
 When any matching table becomes READY, the reservation service triggers a
 notification (and holds the table for the first waiting customer for a
 short grace period).
 Auto-cleanup removes expired waitlist entries.

9. DATA MODEL (Entities & Statuses)
================================================================================
 restaurant-service
   Restaurant        : id, name, cuisine, city, address, rating, avgCostPerHead,
                       openHours, imageUrl, description, features, status(OPEN/CLOSED)
   MenuItem          : id, restaurantId, name, category, price, dietaryTags,
                       spiceLevel, prepTimeMinutes, available, description

 table-service
   DiningArea        : id, restaurantId, name(Floor/Terrace/Lounge), description
   RestaurantTable   : id, areaId, restaurantId, tableNumber, capacity,
                       zone(WINDOW/PRIVATE/OUTDOOR/BAR/FAMILY/LOUNGE), x, y,
                       wheelchairAccessible, quietCorner, cleaningStatus,
                       cleaningStartedAt, cleaningEtaMinutes, version
   CleaningLog       : id, tableId, action, staffEmail, timestamp, note

 slot-service
   TableSlot         : id, tableId, restaurantId, slotDate, startTime, endTime,
                       sessionName(LUNCH/DINNER), status(AVAILABLE/HOLD/CONFIRMED/
                       OCCUPIED/CLOSED), version   <- optimistic locking

 reservation-service
   Reservation       : id, reservationId, confirmationCode, restaurantId,
                       areaId, slotId, partySize, depositAmount, status
                       (HOLD/CONFIRMED/SEATED/COMPLETED/CANCELLED), userEmail
   ReservedTable     : id, reservationId, tableId, tableNumber, zone
   PreOrder          : id, reservationId, status(DRAFT/PLACED/IN_PREP/SERVED/
                       CANCELLED), totalAmount
   PreOrderItem      : id, preOrderId, menuItemId, name, unitPrice, quantity
   TableWaitlistEntry: id, restaurantId, slotId, userEmail, partySize,
                       preferredWindow, status(WAITING/OFFERED/EXPIRED/COMPLETED)

 common (shared DTOs): RestaurantDTO, MenuItemDTO, DiningAreaDTO, TableDTO,
   TableSlotDTO, ReservationDTO, ReservedTableDTO, PreOrderDTO,
   PreOrderItemDTO, CleaningStatusDTO, MatchResultDTO (+ existing
   Auth/User/Payment DTOs)
